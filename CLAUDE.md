# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Development workflow

Every feature or change follows this workflow — keep it in mind from the first line of code:

**When in doubt, ask.** Any uncertainty about *what* to build — the requirement, the desired behaviour, the functional scope — must be resolved by asking the user before implementing. Never guess at intent. *Technical* decisions (architecture, patterns, data structures, naming, test design, refactors), by contrast, are made autonomously to the highest programming standards — do not ask about those, just apply best practice. In short: ask about the functional/feature side, decide the engineering side yourself.

1. **Plan deliberately.** Design so the software stays *extensible* (new cases slot in without rewrites) and *well testable* (logic separable from Android/UI, behaviour reachable by a test). Prefer a reusable building block over a one-off when the same need will recur.
2. **Implement** the plan.
3. **Remove dead code.** Delete now-unused sections, wrappers, imports, and helpers so the codebase stays a clear picture of what's actually in use — no leftovers from the previous shape of the code.
4. **Validate** the change against the requirement (and edge cases) by reading it back.
5. **Write tests** covering the new behaviour (ViewModel logic → JVM unit tests under `app/src/test/`; UI behaviour → Compose tests under `app/src/androidTest/`).
6. **Compile and test from the command line** using the commands below — `assembleDebug` + `testDebugUnitTest` (and `connectedDebugAndroidTest` for instrumented tests when a device/emulator is attached). Don't consider a step done until it builds and tests pass. **`lint` is part of this and must stay at zero errors** — it is the only check that catches an API used above `minSdk` (see the desugaring bullet), which no JVM test can.
7. **Update the docs** — keep this `CLAUDE.md` in sync with new architecture, design decisions, and conventions.
8. **Commit** with a clear, conventional message.

## Build & Test Commands

```bash
# Build debug APK
JAVA_HOME=/opt/android-studio/jbr ./gradlew assembleDebug

# Install on connected emulator and launch
JAVA_HOME=/opt/android-studio/jbr ./gradlew installDebug
/home/anon/Android/Sdk/platform-tools/adb shell am start -n dev.antonlammers.trainist/.MainActivity

# Run all unit tests
JAVA_HOME=/opt/android-studio/jbr ./gradlew testDebugUnitTest

# Run a specific test class
JAVA_HOME=/opt/android-studio/jbr ./gradlew :app:testDebugUnitTest --tests "dev.antonlammers.trainist.ui.overview.OverviewViewModelTest"

```

### Tests

Unit tests live in `app/src/test/` and run on the JVM (`testDebugUnitTest` — no Robolectric). Conventions:

- **Fakes, no mocking library** (`.../fake/`): `FakeFoodEntryRepository`, `FakeGoalRepository`, `FakeFoodSearchRepository`, `FakeWeightRepository`, `FakeCustomFoodRepository`, `FakeSettingsRepository`, `FakeBackupExporter`/`FakeBackupImporter` (each with a `whileRunning` hook so a test can observe the transient `isLoading` state), and for the workout module `FakeExerciseCatalogRepository`, `FakeWorkoutTemplateRepository`, `FakeWorkoutSessionRepository` (the session fake encodes the "at most one active session" invariant).
- Tests use `kotlinx-coroutines-test` + `turbine`. **Every ViewModel has a test class** covering its full behaviour; keep that invariant when adding VM logic. A `WhileSubscribed` StateFlow only computes real values while collected — tests keep it hot with a `backgroundScope` collector and then read `.value`.
- **Pure domain/series logic gets its own test class** (`MacroCalculatorTest`, `InlineHistoryTest`, `RestTimerTest`, `WorkoutMetricsTest`, `TemplateUpdateTest`, `SupersetsTest`, `ExerciseHistoryTest`, `WeightSeriesTest`, `WorkoutSeriesTest`, `OverloadSeriesTest`, `MeasurementSeriesTest`, `ProgressionAdvisorTest`, `WorkoutFormatTest`, `OffSearchQueryTest`, …). The same applies to hand-written content lists — `HelpContentTest`, `TutorialStepTest` — cover the edge cases, not just the happy path.
- Entity↔domain mapping is kept in pure, Android-free helpers so it can be unit-tested without Room (`WorkoutMappers` → `WorkoutMappersTest`; the CSV formats → `BackupImporterTest`/`WorkoutBackupTest`). Repository behaviour is tested with in-memory fake DAOs + a pass-through `TransactionRunner` (`WorkoutRepositoriesTest`).
- **Locale-sensitive formatting in tests**: `currentAppLocale()` falls back to `Locale.getDefault()` on the JVM, so a test asserting formatted decimals must pin `Locale.setDefault()` in setup and restore it afterward (see `WorkoutFormatTest`) — otherwise the expected separator depends on the machine running the test.
- `app/src/androidTest/` holds the **instrumented** tests (run with `connectedDebugAndroidTest` against an emulator/device): `WorkoutMigrationTest` exercises the real Room migrations v7→v8→v9→v10→v11→v12→v13→v14 on Android's SQLite (creates the old DB, runs the migration, asserts new tables/columns + preserved data + FK cascade + the unique (date, type) index the body-measurement upsert relies on). **Every new migration gets a case here** — a JVM test cannot run one, so this file is the only guard against an update destroying installed users' data; the shared `openV7WithSeedData` fixture carries one row per pre-existing table, so add a row there when a migration touches a table it doesn't yet seed. Room's schema JSON is exported to `app/schemas/` (`exportSchema = true` + the `room.schemaLocation` KSP arg); a migration's CREATE statements are copied verbatim from the generated schema JSON so the migrated schema matches the entities exactly.
- **Compose tests live here too**, and the rule for what earns one is "behaviour that only exists inside a real composition, where a ViewModel test cannot follow": `NumericTextFieldTest` (select-all-on-focus — the reason every numeric field goes through that component, and a selection range no JVM test can observe), `WorkoutSetRowTest` (the session set row's local text state: a half-typed `82.` surviving recomposition, and the values adopted on check-off appearing as real text instead of the grey hint) and `MeasurementEntrySheetTest` (the body-measurement sheet's save button being **displayed** — a laid-out-but-off-screen button is a passing ViewModel test and a dead end for the user; see the tall-sheet rule). They drive the composable directly with plain parameters rather than through Hilt — a screen whose behaviour is worth testing should expose a stateless composable to test it with (`SetRow` is `internal` for exactly this).

### Backup & data portability

- **Auto Backup**: `backup_rules.xml` (pre-12) and `data_extraction_rules.xml` (Android 12+) explicitly include `trainist.db` + WAL files — Android backs these up to Google Drive automatically, no code required.
- **Interface seam — `domain/backup/`.** `BackupExporter`/`BackupImporter` are **interfaces** in the domain layer, implemented by `BackupExporterImpl`/`BackupImporterImpl` in `data/backup` (bound in `RepositoryModule`), so `DataViewModel` follows the same "depends only on interfaces" rule as every other VM. The seam carries the backup location as the **string form of a `Uri`**, not a `Uri`: that keeps the interfaces (and therefore the VM) Android-free, so the whole export/import flow is reachable by a plain JVM test — `Uri` round-trips losslessly through `toString()`/`Uri.parse()`, the impls parse it, the UI re-parses it for `Intent.EXTRA_STREAM`, and nothing in between inspects it.
- **Full Backup Export** (`data/backup/BackupExporterImpl`): reads all data — nutrition (food entries, weight entries, daily goal, custom foods), body measurements, and training (custom exercises, templates + slots, sessions + exercises + sets) — and writes a ZIP to `cacheDir` with one named CSV per section (`food_entries.csv`, `weight_entries.csv`, `daily_goal.csv`, `custom_foods.csv`, `body_measurements.csv`, `exercises.csv`, `workout_templates.csv`, `template_exercises.csv`, `workout_sessions.csv`, `session_exercises.csv`, `set_entries.csv`), shared via `FileProvider` + `Intent.ACTION_SEND`. Only **custom** exercises are exported — catalog entries are reproduced by the bundled-snapshot seeding on every install and resolve by stable id.
- **Full Backup Import** (`data/backup/BackupImporterImpl`): opens a user-picked URI, auto-detects ZIP vs single CSV via the PK magic bytes. A ZIP imports every known section by entry name (unknown/missing entries ignored); a single CSV is routed by `detectCsvType` (column presence — see below). The Android IO is kept thin; dispatch/parse/save lives in the Android-free `importZipEntries(InputStream, ImportTargets)` / `importCsvLines(List<String>, ImportTargets)`, unit-tested end-to-end in `BackupImporterTest` (incl. legacy nutrition-only backups, a full training round-trip and a fresh-device relink).
- **Relational training data — stable-key reassembly** (`data/backup/WorkoutBackup.kt`, pure, `WorkoutBackupTest`): the training graph is split into flat CSVs whose **foreign keys are the stable string keys** (`Exercise.stableId`, `WorkoutTemplate.stableId`, `WorkoutSession.stableId`), **never** row ids. On import, `assembleTemplates`/`assembleSessions` re-group the rows (`set_entries` link to their parent by `(session_stable_id, exercise_position)`; rows sorted by `position`), then each root is saved fresh (`id = 0`, target mints its own row ids). Custom exercises are `upsertAll`-ed first so references resolve on a fresh device. The relational sections only reassemble as a whole ZIP; a lone `exercises.csv` imports standalone, the other five training CSVs are recognised-but-no-op on their own.
- **CSV type detection** (`detectCsvType`): identifies a CSV by a unique column. Training sections are matched **first** (`set_entries.csv` also carries `weight_kg`, so it must win over the weight-entries rule):
  - `is_custom` → `EXERCISES`; `template_name` → `WORKOUT_TEMPLATES`; `target_sets` → `TEMPLATE_EXERCISES`; `is_active` → `WORKOUT_SESSIONS`; `superset_group_id` → `SESSION_EXERCISES`; `exercise_position` → `SET_ENTRIES`; `value_cm` → `BODY_MEASUREMENTS`
  - `food_name` → `FOOD_ENTRIES`; `weight_kg` → `WEIGHT_ENTRIES`; `kcal_per_100g` → `CUSTOM_FOODS`; `kcal` (without the above) → `DAILY_GOAL`
- **CSV formats** (all pure Kotlin, one object per section, name-based columns; `CsvFormat.parseHeaders` is the shared header parser): `CsvFormat` (food entries, incl. `tag` → `FoodTag.parse`, missing → `NONE`), `CustomFoodCsvFormat`, `WeightCsvFormat` (`date`, `weight_kg`, `timestamp_ms`), `GoalCsvFormat` (single row; optional `target_weight_kg` + optional `bmr_sex`/`bmr_age_years`/`bmr_height_cm`/`bmr_activity_level`, all-or-nothing via `BmrProfile.fromParts`), `BodyMeasurementCsvFormat` (`date`, `type` → `MeasurementType.parse`, `value_cm`; one row per (date, type), like `SetEntryCsvFormat`'s `type` column but for `MeasurementType` — imports via `BodyMeasurementRepository.save(date, mapOf(type to valueCm))`, same as the entry sheet), `ExerciseCsvFormat`, `WorkoutTemplateCsvFormat`, `TemplateExerciseCsvFormat` (`set_types` = planned `SetType`s joined by `|`; older backups fall back to `target_sets` NORMAL sets; `superset_group_id` = the planned grouping, missing → null = stands alone), `WorkoutSessionCsvFormat` (optional `template_stable_id`), `SessionExerciseCsvFormat`, `SetEntryCsvFormat`. List cells (muscles/instructions/set types) are `|`-joined — one line per row; an embedded newline would break the line-based reader.
- **FileProvider** authority: `dev.antonlammers.trainist.fileprovider`, paths in `res/xml/file_paths.xml` (cache dir).

### Backup schema evolution — backward compatibility contract

All CSV parsing is name-based (column order irrelevant). This gives forward and backward compatibility for free, as long as these rules are followed:

| Change | Export (`toRow` / `HEADER`) | Import (`fromRow`) |
|---|---|---|
| **Add a column** | Add constant to the format object, add to `HEADER` and `toRow` | Read with a sensible default for missing values — old exports still parse |
| **Remove a column** | Remove from `HEADER` and `toRow` | Remove the read; unknown columns are ignored, so new exports still parse in old app versions |
| **Rename a column** | Write both old and new names for at least one release, then drop the old | Read the new name with fallback to the old until the transition ends |
| **Add a new data type** | New `*CsvFormat` object + ZIP entry name in `BackupExporter` | New `CsvType` variant + detection rule in `detectCsvType` (more-specific rules before any that shares a column), handle in `importZipEntries` + `importCsvLines` |
| **Add a relational data type** | Flat CSVs whose foreign keys are **stable string keys** (never row ids); one section per table | Reassemble the graph in a pure helper (like `WorkoutBackup`), save each root with `id = 0`; keep it a whole-ZIP operation |
| **Change the ZIP container format** | — | Extend `isZip` / add a new container detection path; keep old paths for legacy files |

**No explicit version field is needed.** Structural detection (column presence, ZIP magic bytes, entry names) is sufficient. Only introduce a version field if two formats become structurally ambiguous.

**Referential integrity across devices.** Relational backups never serialise auto-increment row ids — all cross-row references use stable string keys, so a backup rebuilds correctly on a device whose row ids differ.

### Key design decisions

- **Domain layer is Android-free.** ViewModels depend only on `domain/repository` interfaces. Swapping the data source touches only `data/` and `di/`.
- **Bottom navigation — four tabs** (`AppNavigation`, `bottomNavItems()`): **Ernährung** (`Screen.Overview`), **Training** (`Screen.Workout`, the template list), **Statistik** (`Screen.Stats`), **Einstellungen** (`Screen.Settings`). Icons active = `Icons.Rounded.*`, inactive = `Icons.Outlined.*` (Restaurant / FitnessCenter / BarChart / Settings). The nav is **icon-only** — no `label`; the localized name lives on as each icon's `contentDescription`. Goal editing lives behind the Settings hub (no Goals tab). Any route not in `bottomNavItems` (`AddFood`, `BarcodeScanner`, `ExerciseCatalog`, `ExerciseDetail`, `TemplateEditor`, `WorkoutSession`, `WorkoutHistory`, `Goals`, `Help`) hides the bar.
- **Theme isolation — "Ink & Paper".** Replacing `ui/theme/Color.kt`, `Theme.kt`, and `Type.kt` restyles the entire app. Fixed monochrome color system (no Material You, `dynamicColor = false`): dark = "Ink", light = "Paper". Colour is reserved for data. `Color.kt` holds the `Ink*`/`Paper*` palettes (paper/bg/surface/surface2/line/text/text2/text3), the mode-independent `AccentLilac` (`#B79FCB`, `primary`/`secondary`) + `OnAccentInk`, the pastel macro colours (`CalorieColor`/`ProteinColor`/`CarbsColor`/`FatColor`) and the clean-eating tag colours. `Theme.kt` maps these onto the Material3 schemes (`surfaceContainerLowest` = chrome, `outlineVariant` = hairline, `error` = unhealthy tone). The base XML theme `Theme.Trainist` must stay **DayNight-aware** (`values/themes.xml` light + `values-night/themes.xml` dark window background) — otherwise the window background bleeds through as a hairline at the bottom-nav seam in dark mode.
- **Which shade — `ThemeMode` (SYSTEM/LIGHT/DARK).** `domain/model/ThemeMode` is the persisted appearance choice; its pure `resolveDark(systemInDarkTheme)` is the single place the choice becomes a dark/light decision, so the UI only supplies `isSystemInDarkTheme()`. Read via `ui/theme/ThemeViewModel` (a pass-through onto `SettingsRepository.themeMode`) in **two** places: `MainActivity` (wrapping the whole app in `TrainistTheme(darkTheme = …)`) and the Settings appearance row. That is why the repository exposes it as a **`StateFlow`** rather than a suspend getter like every other setting — a change in one surface has to reach the other live, and the current value must be readable synchronously or a pinned shade flashes the opposite one for a frame on cold start. Switching applies instantly; no activity recreation (unlike the language picker).
  - **Two things live outside the Compose hierarchy and still follow the *system* uiMode on their own**, so `MainActivity.applyWindowAppearance(darkTheme, chrome)` re-applies both against the *resolved* shade whenever it changes: `enableEdgeToEdge`'s system-bar icon contrast (re-called with `SystemBarStyle.auto(…) { darkTheme }`; its default scrim constants are private, so they're spelled out) and the window background (`window.setBackgroundDrawable` with `surfaceContainerLowest`, overriding the DayNight XML theme). Without it, forcing light on a dark device leaves white status-bar icons on a light bar and a dark hairline under the bottom nav. Anything else that reads `uiMode` outside Compose needs the same treatment; the Glance widget deliberately does **not** — it lives on the launcher and follows the system there.
- **Typography — three downloadable Google fonts** (`ui/theme/Type.kt`): `NewsreaderSerif` (display/headline/title: screen titles, big numbers), `HankenGroteskSans` (body + `labelLarge`), `JetBrainsMono` (`labelMedium`/`labelSmall` uppercase micro-labels with wide tracking, e.g. `KCAL`). Loaded at runtime via the Google Fonts provider (`font_certs.xml`) — no bundled font binaries; requires Google Play Services at runtime.
- **Icons — Material Symbols Rounded.** All icons use `Icons.Rounded.*` (not Filled/Default). Reach for the Rounded variant when adding a new icon.
- **Numeric input — `ui/components/NumericTextField`.** *Every* numeric field uses it, never a bare `OutlinedTextField`. On focus it **selects its whole content** so a pre-filled value is overwritten by simply typing. String-based `value`/`onValueChange` API (callers parse, accepting comma or period via `normalizeDecimal`); `decimal = false` for whole-number keyboards; nullable `label`; optional `textStyle`/`leadingIcon`/`placeholder` slots (the placeholder shows grey inline-history hints in the session).
- **Drag-to-reorder — `ui/components/DragReorderColumn`.** The one reordering pattern app-wide (template editor slots, templates list, stats cards — **not** session sets, which are a fixed top-to-bottom list with no drag handle, kept intentionally simple): long-press the row's drag handle (`Icons.Rounded.DragIndicator`, haptic tick), drag, settles on release. Renders a plain non-lazy `Column` (nest it as a single item inside an outer `LazyColumn`); takes `items`/`key`/`onMove(from, to)` plus an `itemContent` slot receiving a `rowModifier` (apply to the row container — carries drag translation/elevation) and a `dragHandleModifier` (apply only to the handle so the gesture never fights the row's own controls). While dragging it calls `onMove` **once per adjacent step** (whenever the dragged row crosses a neighbour's mid-height), so the ViewModel side is a simple adjacent swap persisted continuously — no "commit on drop" step. Internally each row **must be wrapped in `key(itemKey) { … }`** — without it the non-lazy `Column` identifies children by slot, so the first swap restarts the row's `pointerInput` and cancels the in-progress gesture. `key` must be genuinely unique per row (duplicates of the same exercise are allowed), so rows carry stable ids (`TemplateSlot` a synthetic negative `newId()`; session/set entries already have stable ids).
- **Settings hub** (`ui/settings/SettingsScreen`): a short list of **grouped rows**, not a scroll of inline forms — three labelled groups (ERNÄHRUNG / BENACHRICHTIGUNGEN / APP) over a donation button and a version footer, fitting on one screen without scrolling. The rule for what goes where: **a single control → inline** (the reminder `Switch`), **a handful of actions → a bottom sheet over the hub** (language, backup, support), **a real editing form → its own screen** (`Screen.Goals`, the only settings route; absent from `bottomNavItems`, so the bar hides itself). Rows report their current value inline (`goal.kcal`, the picked language) so the common case needs no tap. The hub hosts `GoalsViewModel` (for the calorie preview only), `DataViewModel` (reminder toggle **and** the backup sheet) and `LanguageViewModel`.
  - **Row vocabulary** (`ui/settings/SettingsRow.kt`): `SettingsGroupLabel` (mono-uppercase caption) + `SettingsGroup` (bordered card) + `SettingsRow` (leading icon, title, optional supporting line, optional `value`, `trailing` slot) + `SettingsRowDivider` (hairline inset past the icon) + `SettingsOptionRow` (the radio row behind every "pick exactly one" sheet — language, appearance; the whole row is the tap target). `onClick` is nullable so a switch row stays non-clickable as a whole. - **BMR/TDEE calculator** (`ui/bmr/`, `domain/BmrCalculator.kt`): a 6-step wizard (sex → age → height → weight → activity level → goal) computing calorie needs via **Mifflin-St Jeor**. `BmrCalculator.bmrKcal` (male: `10×kg + 6.25×cm − 5×age + 5`; female: `…− 161`) → `tdeeKcal` (× one of 5 standard activity multipliers, `ActivityLevel` 1.2–1.9) → `goalDeltaKcal` → `goalKcal` (floored at `max(bmr, 1200)` so a recommendation never drops below resting energy expenditure or an absolute safety floor). Macro suggestions reuse the existing `MacroCalculator` (protein/fat from body weight, carbs fill the rest) — no separate macro logic.
  - **The goal delta is a fraction of TDEE, not a fixed number** (`WeightGoal`: LOSE −18 %, clamped −700…−250; MAINTAIN 0; GAIN +10 %, clamped +150…+400). The clinical 500 kcal/day figure is sound *at a certain body size* — ~17 % of a 100 kg man's TDEE but ~29 % of a 55 kg woman's, i.e. ~0.8 % of her body weight per week, past the 0.5–0.75 % associated with holding onto muscle, and it lands her intake on the BMR floor where 1.6–2.2 g protein/kg gets tight. A fraction self-scales; the clamps stop a huge TDEE from becoming a crash diet and a tiny one from producing a change that disappears in ±1 kg of daily weight noise. This also keeps the recommendation consistent with `ProgressionAdvisor`, which later judges the user against a *measured* body-weight slope (`DEFICIT_KG_PER_WEEK`) — a flat −500 could recommend a rate the overload card then reads back as the cause of stalled strength.

It is derived from the **final** (possibly floored) target, not the nominal delta, so a raised recommendation reports the smaller change it will actually produce; the line hides below 0.05 kg/week, where it would round to 0.0. The rule overestimates long-term loss (expenditure falls with weight) — it's an order of magnitude for the first weeks, and the KDoc says so. `BmrCalculatorViewModel` (`BmrStep` enum + `BmrCalculatorUiState`) owns per-step validation (`canProceed`) and the live `result()` preview; **persists the profile** (sex/age/height/activity level, via `BmrProfile` on `DailyGoal`) the moment it's complete (leaving the ACTIVITY step) independent of whether GOAL is ever reached, so backing out still prefills next time. **Body weight is deliberately not persisted** — the calculator's weight field prefills live from the most recent `WeightEntry` instead (`weightRepository.allEntries().maxByOrNull { it.date }`), since freezing a stale weight snapshot into the profile would go stale. `BmrCalculatorWizard` (the step UI) is hosted two ways: inline by onboarding's local step machine (mandatory on that path — see below) and via the pushed `Screen.BmrCalculator` route from `GoalsScreen` (`BmrCalculatorScreen`), so it's re-runnable any time to update goals.

  - **Progressive Überladung** (`ui/stats/OverloadSeries.kt` + `OverloadCard.kt` + `domain/ProgressionAdvisor.kt`) — the "am I getting stronger *overall*?" card, answering in one number what Kraftverlauf answers per exercise, plus situational coaching:
    - **Chain-linked strength index, not an average of 1RMs.** Raw 1RMs aren't comparable across exercises (a 120 kg squat drowns out a 15 kg raise) and an average over "whatever was trained this week" swings with the split. Instead: weekly buckets → best Epley 1RM per (week, exercise) → each week's growth is the **geometric mean of the per-exercise ratios against that same exercise's own previous observation**, chained onto the previous level from `BASE_INDEX` (100). So only an exercise compared **with itself** moves the index — a rotating split, a new exercise or a dropped one can never fake a jump. Guards: a first appearance contributes nothing (it only starts counting from its second), a previous observation older than 4 weeks is dropped rather than squeezed into one weekly step, and per-step ratios are clamped to 0.8–1.2 so a mistyped 500 kg can't destroy the series.
    - **Own fixed window** — `OverloadSeries.WINDOW_WEEKS` = 12, deliberately **ignoring the time-range chips** (which the card states inline as "Letzte 12 Wochen"). A 7-day view of a trend is noise, so this card never offers one. Consequence for the VM: it lives in its **own** `combine` (sessions + catalog + all weigh-ins + food entries over *its* window + goal), recombined onto `chartState` like `_cardOrder` — switching the range must not recompute it.
    - **`ProgressionAdvisor` (pure, `ProgressionAdvisorTest`)** turns measured facts (`ProgressionFacts`) into a `ProgressionTrend` + up to 3 ranked `ProgressionAdvice` constants. Rules, in order of importance: (1) **never conclude from a small window** — below 3 trained weeks *or* 6 sessions the only output is `COLLECT_MORE_DATA`, no causal claim at all; (2) a **dead band** around zero (≥ +2 % = progress, ≤ −3 % = decline — asymmetric, because calling a regression needs the stronger evidence) since day-to-day 1RM variation is a few percent; (3) **measured signals beat assumed ones** — "in a deficit" is read from the *body-weight trend* (least-squares slope, ≥ 3 weigh-ins over ≥ 21 days) and only falls back to logged kcal vs. goal, because a goal may itself be a deliberate cut; intake means use **logged days only** (≥ 21 of them) so forgetting to track never reads as a crash diet. Maintaining strength *while* losing weight is reported as a success (`EXPECTED_IN_DEFICIT`), not a plateau. Thresholds follow current literature (1.6–2.2 g protein/kg, 10–20 hard sets per muscle per week at 0–3 RIR, ≤ 0.5–0.75 % body weight lost per week, deload after ~4–8 weeks) and are named constants on the object.
    - Advice is **structured, never text**: the VM emits enum constants, `OverloadCard` maps them to string resources (the app-wide "no display strings in a ViewModel" rule).
- **Open Food Facts — two hosts, two Retrofit instances.** Barcode lookup uses `https://world.openfoodfacts.org/` (`OpenFoodFactsApi`, `api/v2/product/{barcode}`, `status == 1` = found). Just as important: **never pass `sort_by`** — `-unique_scans_n` discards the relevance score and answers "milch" with Lindt chocolate and Alpro oat drink. The service's default is relevance; leave it alone.

Language follows the app setting; the country answers "where does this person buy groceries", resolved by the pure `CountryResolution.resolve` in this priority: the user's **explicit choice** in Settings → **mobile network** country → **SIM** country → **device region**. The device region is deliberately *last*: it is a language preference wearing a country, and someone who set their phone to "English (United States)" while living in Berlin is not shopping in American supermarkets. Neither telephony call needs a permission and both are simply empty on a Wi-Fi-only device. The tag is derived from `Locale` rather than a hard-coded table — English country name, accent-folded and slugified (`CI` → `en:cote-d-ivoire`), validated against `Locale.getISOCountries()` because an unassigned code resolves to the literal name "Unknown Region".

The country list is built in the UI layer from `Locale`, not held in the ViewModel: the names have to be localized anyway, and a VM holding 250 translated strings would break the "no display text in a ViewModel" rule for nothing.

The search service is a shared, rate-limited community resource; one request per keystroke would be both rude and slower than useful. `RemoteSearchState` keeps `failed` distinct from an empty `results` — "nothing found" and "couldn't reach Open Food Facts" are different messages, and only one is worth retrying.

Without the pin, the window resize *and* the reported IME inset double up and the panel floats a keyboard-height too high. This is the general fix pattern for this situation — don't fight the resize with padding math.

- **Rest timer** (`domain/RestTimer` + `notification/RestTimer*`): checking off a set starts a rest countdown (per-exercise `Exercise.restSeconds`, else 180 s default). Design constraints that shaped it:
  - **Pure state** (`domain/RestTimer`): anchored to a wall-clock `endAtMs`; remaining time is always recomputed from "now" (correct across backgrounding); `start`/`paused`/`resumed`/`adjusted` are pure transitions.
  - **VM stays Android-free**: `WorkoutSessionViewModel` owns the timer state and emits one-shot `RestCommand`s on a channel; the screen mirrors them into the Context-holding `RestTimerService`. There are exactly two: **`Sync`** carries the *complete* timer state (`exerciseName`/`totalSeconds`/`endAtMs`/`pausedRemainingMs`) and is emitted on **every** transition — start, resume, pause, ±15 s — so the service never reconstructs anything and an adjustment always moves the real alert instant; **`Stop`** ends the rest (skip/finish/discard). Every transition funnels through the single private `applyRest()` write path (set state → persist anchor → emit `Sync`). There is deliberately **no** "expired" command — the service owns the moment the countdown hits zero. The VM's `restTimer` flow is **display-only**: it is bound to the screen's lifecycle, so it must never be responsible for the alert. The in-app `RestTimerBar` shows mm:ss + progress with ±15 s / pause-resume / skip; it rides in the Scaffold's **`topBar`** slot (a `Column` under the back/finish `TopAppBar`, progress line attached to it, hairline below), not the `bottomBar` — it is what the user watches between sets, and at the bottom it competed with the set rows and disappeared behind the keyboard while a weight was being typed; each exercise-card header carries a rest-duration override chip (persisted via `catalog.upsert` with a new `restSeconds`).
  - **Survives leaving the session**: the anchor is persisted onto the session (`restExerciseStableId`/`restTotalSeconds`/`restEndAtMs`/`restPausedRemainingMs`, null when idle) on every transition; on `init` an active session's anchor is restored (dropped + cleared if already expired).
  - **The service owns the countdown — no alarms at all** (`notification/RestTimerService`): a **long-lived foreground service** runs for the *entire* rest and fires the alert itself, on the second. Nothing else can promise that: a countdown in the UI layer dies with the screen's lifecycle (so it never fires while backgrounded — that was the old "notification ticks into the negative" bug), and an *inexact* alarm (the only kind this app may use) is deferred by Doze by seconds to minutes. `AlarmManager` is gone from the app entirely. The service loop recomputes the remainder from the **wall clock** every pass and trims the final `delay` to it, so an overshooting tick cannot drift the alert instant; a **partial wake lock** (acquired for `remaining + alert + margin`) keeps the CPU from suspending with the screen off. Verified on an emulator: alert lands at +30.8 s of a 30 s rest with the app foregrounded, backgrounded, **and** with the screen off; two ±15 s taps move it to +60.6 s; a pause freezes it indefinitely and resume fires the exact remainder.
  - **Still no exact alarms (Play policy)**: `USE_EXACT_ALARM`/`SCHEDULE_EXACT_ALARM` remain deliberately **undeclared** — Google Play restricts them to apps whose *core functionality* is an alarm clock/timer/calendar, which a training app is not (Play-Console exact-alarm declaration = "No"). The foreground service delivers the same precision without them.
  - **FGS type `specialUse`** (manifest `android:foregroundServiceType="specialUse"` + `FOREGROUND_SERVICE_SPECIAL_USE` permission + a `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` of `rest_timer_between_sets`): the honest type for a rest-between-sets countdown — it is neither media playback nor any other predefined category (the previous `mediaPlayback` declaration was for a service that only played ~2 s of audio). **This needs a justification in the Play Console's foreground-service declaration.** `startForeground` only passes `FOREGROUND_SERVICE_TYPE_SPECIAL_USE` from **API 34** (`startForegroundCompat`) — passing a type the platform cannot match to the manifest throws.
  - **Killed with the app**: swiping the app out of the recents kills the service with the process, so that rest's alert is forfeited (an explicitly chosen trade-off — self-restarting is unreliable on OEM battery managers). The persisted anchor still restores the timer on the next launch, and `restoreRestTimer` re-runs `applyRest()` rather than only restoring state, so the service is running again even after a process death.
  - **Ongoing notification** (silent LOW channel `rest_timer_ongoing`): custom content view (`notification_rest_timer.xml`) with a large countdown — running uses an embedded `Chronometer` counting down to the end instant (Android keeps it live without re-posting), paused shows a frozen mm:ss. Text colour is set **explicitly per shade theme** (`uiMode` night mask) — `?android:attr/textColorPrimary` does not reliably resolve to the shade's theme across OEMs.
  - **Expiry alert** (`RestTimerService.fireAlert`): the service promotes its **own** bundled `res/raw/rest_over.ogg` (~0,9 s, generated with ffmpeg — no system ringtone, so the app always sounds like itself) plus a short double-buzz, capped at 2 s (`ALERT_DURATION_MS`). Audio plays on **`USAGE_ALARM`** (the alarm stream — audible with the ringer silenced and independent of the media volume) while holding `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`, so running music *ducks* instead of stopping. Vibration goes through `Vibrator` directly with alarm usage, never through a notification channel — so the channel stays fully silent and nothing ever doubles up. The alert notification is posted via `startForeground` under its own id, which keeps the service a legal FGS while it plays; afterwards `STOP_FOREGROUND_DETACH` + `RestTimerNotifier.repostExpiredDismissible` re-posts it plainly, because a `startForeground` notification carries **`FLAG_NO_CLEAR`** that detaching does not drop (it would otherwise be un-swipeable and clearable only by tapping into the app).
  - **Notification-channel rules** (general): a channel's importance/sound/vibration are **immutable once created** — changing any of them requires a **new channel id** (hence `rest_timer_alert_v4`, now fully silent since the service makes the noise itself; `IMPORTANCE_HIGH` is kept so it still pops as a heads-up). Mutable `name`/`description` self-heal on the next `ensureChannels` call, which runs before every build (this is also what re-localizes channels after a language switch). The alert uses its **own notification id** (2003) distinct from the ongoing one (2002) — Android won't move a posted notification to a different channel on update, so the alert must be a *fresh* notification to actually alert. `RestTimerNotifier.cancelAll(context)` dismisses both; `RestTimerService.stop(context)` (skip/finish/discard) stops the service and calls it.
  - Tapping any rest-timer notification opens `MainActivity` with `EXTRA_OPEN_WORKOUT_SESSION`; `AppNavigation` reads it and navigates to `Screen.WorkoutSession.start(0)` (resumes the active session regardless of the templateId arg). `MainActivity` deliberately cancels **nothing** on that extra — the *ongoing* countdown notification carries the same extra, so tearing anything down there would kill a rest that is still running.
- **Workout module** — domain models are Android-free: `Exercise` (catalog + custom), `WorkoutTemplate`/`TemplateExercise`, `WorkoutSession`/`SessionExercise`/`SetEntry`, enums `ExerciseType` (WEIGHT_REPS/BODYWEIGHT — additively extensible), `SetType` (WARMUP/NORMAL/DROP/FAILURE), `Mechanic` (COMPOUND/ISOLATION, nullable). In-session additions get synthetic negative client ids (`newId()`) as stable UI keys (never persisted — mappers mint real ids). `uiState` joins the session with the catalog (names/types), the session history (inline hints) and the resolved body weight (from `WeightRepository`, for bodyweight-exercise calculations). A `finished` StateFlow drives `popBackStack`. The `clock: () -> Long` is injected via a secondary constructor (default `System::currentTimeMillis`) so tests use a fixed clock.
  - **Supersets** (`domain/Supersets.kt` + `domain/model/SupersetMember` + `ui/workout/SupersetUi.kt`): two or more exercises performed back to back. A superset is defined as a **maximal run of adjacent members sharing one non-null `supersetGroupId`** — adjacency is part of the definition, so a removal, insertion or reorder can never leave a "group" whose members are pages apart.
    - **`normalize` is the only writer of group ids.** Every operation ends in it; it re-derives ids from adjacency alone (runs of ≥ 2 → renumbered 1..n in list order, everything else cleared). Two invariants fall out and are relied on elsewhere: a group can never have **one** member (a lone survivor dissolves itself), and ids are canonical, so `groupOrdinals` is a plain `id - 1` and a group's display letter never jumps when an unrelated group is dissolved. Call it after **any** structural change — the session VM's `reindexExercises` and the editor's `removeExercise`/`moveSlot` all do.
    - **One implementation for plan and performance.** `SupersetMember<T>` (`supersetGroupId` + `withSupersetGroupId`) is implemented by `TemplateExercise`, `SessionExercise` **and** the editor's `TemplateSlot`, so `Supersets` is generic and the planned and performed grouping cannot drift into two near-copies. Ids are meaningful only *within one list*; nothing outside references them.

The domain emits an **ordinal**, never a letter — `supersetLetter` is the UI's job, per the app-wide "no display strings in the domain/VM" rule.

Session and template group ids both count from 1, so merge shifts the session's ids past the template's max before normalizing — otherwise a skipped slot's group and a performed slot's group would collide.

- **App versioning — git-derived build counter.** `versionCode = git rev-list --count HEAD` (computed at configure time), `versionName = "1.0.<count>"` — nothing to bump by hand. `BuildConfig.VERSION_NAME` shows in the Settings `VersionFooter`. `scripts/git-hooks/prepare-commit-msg` stamps each commit message with the `Version: 1.0.<N>` trailer it will produce (skips if already present, so `--amend` doesn't double it); it's installed in this checkout, but **a fresh clone must copy it in manually** (`cp scripts/git-hooks/prepare-commit-msg .git/hooks/`). **CI checkouts must fetch full history** (`fetch-depth: 0`) — a shallow clone would make every CI build report `1.0.1`; the workflows all do.
